## 1. Goal（一句话）

**建一个能自己转的自进化循环，任务载体是「放积木」。**

### 1.1 为什么把框架从「采数据」改成「自进化循环」

原来这份文档的交付定义是「能自主执行 + 能采数据」，把模型训练推给「下一阶段」。
这个切法有一个问题：**它把循环里最难的两环（判定、和决定下一个试什么）留在了范围之外，
而这两环恰恰决定前两环要怎么造。**

循环是：

```
提出实验 ──▶ 执行 ──▶ 判定 ──▶ 决定下一个试什么 ──┐
    ▲                                          │
    └──────────────────────────────────────────┘
```

按「采数据」的框架，你只需要「执行 + 落盘」，判定可以事后人工看视频，
重置可以人工摆回去 —— 都不是阻塞项。
按「自进化循环」的框架，**这两件事立刻变成地基**：

- **判定器不再是闸门，是地基。** 离线训练里 judge 错了只是噪声；循环里 judge 错了会被
  放大 —— 它决定下一个采什么，错判把采样引到错误区域，再用更多错数据确认自己。
- **重置成了真正的天花板。** 人工重置下，采样率上限 = 人的手速。而**原来的文档里
  完全没有「重置」这一项**（grep `05_experiment_protocol.md`：0 次命中）。

量级差别不是修辞：自动重置 vs 人工重置约 **10×**（~32 000 vs ~3 100 episode/周），
而且按 30% 成功率算，拿 1000 条成功 episode 需要的**人力（18.5 h）超过机器人时间（13.9 h）**。

> **成功率 30%、没有自动重置的情况下，「自进化」会退化成一次极其昂贵的随机搜索。**

完整推导见 [`09_self_evolution_bottlenecks.md`](09_self_evolution_bottlenecks.md)；
施工方案见 [`07_self_improving_loop.md`](07_self_improving_loop.md)。

## 3. 本阶段的成功判据

分两层。**S 层是单条 episode 的能力，L 层是循环的能力** —— 原来只有 S 层，
L 层是这次改写补的，而且 L 层才是本阶段真正的交付。

### S 层：单条 episode

- **S1 感知**：能从图像中拿到桌面上每块积木的位置（至少 2D + 深度，或 3D 位姿）
- **S2 抓取**：夹爪能闭合并夹住一块积木，抬起 ≥ 5 cm 不掉落
- **S3 放置**：能把积木放到指定目标格位，落点误差 ≤ 1 cm，不推倒邻块
- **S4 自主**：S1–S3 由程序闭环触发，**不依赖人在 LiveKit 手柄上遥操**
- **S5 采集**：整段轨迹按 LeRobot dataset schema 落盘（图像 + 关节 + EE 位姿 + 夹爪 + action），可回放
- **S6 可重复**：连续 N 次试验（建议 N=20）成功率与失败模式被记录下来

### L 层：循环（本阶段的真交付）

- **L1 自动判定**：judge 给出 成功 / 失败 / **弃权** 三态，且 verdict 随 episode 落盘。
  分层设计：场景级用头部 ZED，末段用腕部相机 + 夹爪 `pos_mm` 卡滞
- **L2 判定器可靠性**：在一个**冻结的 golden set** 上，judge 的系统性偏置 **≪ 5 pp**。
  依据：`p=0.30` 时 5 pp 偏置会让第 84 条之后的采集**对判断进展毫无价值**（`09` §1.2）
- **L3 自动重置**：失败后的场景**不需要人介入**即可开始下一条 episode。
  实现方式 = 逆向 episode（一排 → 散乱），且散开 = **把每块放到随机采样的目标位姿**，
  它同时是重置器、域随机化器和课程表旋钮
- **L4 MTBH ≥ 8 h**：平均人工干预间隔 ≥ 8 小时，即能跑完一整夜无人。
  反解 = **不可恢复率 < 0.052 %/episode**（`09` §4）。
  **用写死的脚本策略先测这一项，不达标先修物理布置、不要修算法**

## 4. 目标之外（本阶段明确不做）

- 不做移动底盘导航去别的桌子。⚠️ 但**底盘必须先挪一次到位再钉死** ——
  感知实测积木在 `x≈0.55 m`，臂的可达带只有 `x=0.22~0.46`，
  所以 `04` 的 D3 **由「可选策略」升为「一次性前置条件」**（见 `07_perception_scheme.md` §4）
- 不做双臂协同装配
- 不做大规模策略训练。⚠️ 但**循环必须闭合** —— "判定"和"决定下一个试什么"在范围**内**（§1.1）
- 不做非刚体、不做未知类别物体

### 5.1 B3 已解决 —— 夹爪是好的，我之前整个诊断方向是错的

我原先判定"NiMotion 驱动器在 CAN 上不发帧，属供电/接线，修法在物理层"。**这是错的**，
而且错得有代价：它把结论推向"只能等人去现场接线"，实际上纯软件就能解决。

正确的结论链（每一步都有实测）：

1. 夹爪**根本不在 CAN 上**。can1+can2 全部 127 个 node id 做 SDO 探测，只找到 14 个手臂驱动器。
2. 真实硬件是 **UFactory Gripper G2，走 Modbus RTU / RS485**：
   `/dev/ttyUSB0` = **右手**、`/dev/ttyAMA5` = 左手，slave id 8 @ 2 000 000 baud。
   （左右是靠单独抖 `ttyUSB0` 十次、人在旁边看着确认的。**静态看开口没用** ——
   未动过的爪子停在 548/840 ≈ 65% 开，肉眼和全开分不出来。）
3. 根因是 **`Fn100` 使能寄存器 = 0，从来没人使能过**，

### 5.2 B9 已证伪 —— 手臂反馈就是弧度，我错了

我上一版在这里断言"`/joint_states` 手臂位置不是弧度，是 `编码器刻度 × 95.8738 / 减速比`，
所以不能做 FK/IK、不能下发臂指令"。**这个结论是错的，而且是被它自己提议的那个实验推翻的。**
`scripts/arm_unit_probe.py` 的实测（2026-08-07）：

| 量 | 值 |
|---|---|
| 指令 `right_arm_3_joint` | **+0.174533 rad**（= +10.0°）|
| 反馈增量 | **+0.174526** |
| **系数 = 反馈 / 指令** | **1.0000** |
| 参照 | 57.2958 → 反馈是度；**1.0 → 反馈是弧度** |

5 个分步点全部精确跟随，回零后 `max|q| = 0.000008`。
**读写单位一致，`/joint_states` 可以直接喂 FK/IK。** B9 关闭。

**那 95.8738 那套算术是怎么回事？** 它不是解析 bug —— `值 × 减速比` 确实全是它的整数倍，
比值命中 5 位有效数字。真相是**时序**：那次读数发生在
`astrabot_arm_forward_position_controller` **收到第一条指令之前**，
臂的反馈还是未锁存的原始执行器状态（所以 9 个值超出 URDF 限位，而臂物理上就垂在身侧）。
探针发出第一条指令之后，14 路全部落到 `±0.000006` 并稳住
（8 秒 1530 帧，极差 3 µrad，两个发布者 `astrabot_mrt` + `joint_state_broadcaster` 数值一致）。

> ✅ **留下来的操作规则**（这才是那次踩坑的真正教训）：
> **先发一条指令，再信反馈。** 绝不要在控制器刚起来时用 `/joint_states`
> 去构造"保持当前位姿"的指令 —— 那正是把 `left_arm_6` 发到 544°（限位 ±1.57 rad）的方式。
> `astrabot_arm_forward_position_controller` 吃 14 个关节**一整个数组**（左 7 + 右 7），
> 动右臂必须同时给左臂发值，所以这个坑很容易踩。安全的起点是**全 14 路发 0.0**：
> 0 在每个关节限位内，且 FK 已证 `q=0` 就是"手臂垂在身侧"（实拍一致），所以那是个小动作。
>
> 该话题另有 `astrabot_mrt` 和 `astrabot_actuator_sdk` 两个发布者，静默但可能抢发 ——
> 下发前先确认没有第三方流量。叠加 B8（`effort` 全 `.nan`）→ **撞了不会自己停**，
> 幅度要小、人要在旁边。

### 5.3 B10 —— 桌子在机器人伸不到的地方

用户实测：**桌沿到机器人约 0.56 m**，**桌高 0.75 m**（卷尺）。
把这两个数代进 `results/workspace_spec.md` §3 的桌沿敏感性表（已按 0.75 m 重算），
结果不是"区域变小"，是**归零**：

| 桌沿 x (m) | 右臂可行格 | 备注 |
|---|---|---|
| +0.34 | 18 | 60×90 mm 矩形，摆 L 形够 3 块 |
| +0.46 | 2 | ❌ |
| **+0.49** | 0（有 3 格有 IK 解但间隙全 < 30 mm）| **加门槛后的极限** |
| **+0.52** | 0（**连 IK 解都没有**）| **前伸运动学硬极限** |

| 0.22（满配）| 0.34 m | ❌ 上限 0.227 | **推近 11.3 cm** | 40 格，150×90 mm |

### 5.4 B11 —— 底盘不动：推行模式按下（当前第一阻塞，需人动手）

`/cmd_vel` 的链路**是通的，一路通到底盘**，问题在最后一环。逐段实测：

| 环节 | 实测 | 判定 |
|---|---|---|
| `/cmd_vel`（Twist）→ `nav_cmd_vel_adapter` | 发出 41 帧 0.05 m/s | ✅ |
| `/ecu/cmd_vel`（**TwistStamped**）→ `xr1_chassis` | **41 帧，非零 41，max = 0.0500** | ✅ 适配器没有拦 |
| `/ecu/cmd_vel_smoothed`（底盘自己的回显）| **41 帧，非零 0，max = 0.0000** | 🔴 **底盘把每一帧都归零了** |
| `/odom` | Δx = **+0.00 mm** | 🔴 没动 |

> ⚠️ **这里我犯过一个错，值得记下来**：第一次监听 `/ecu/cmd_vel` 时我按
> `geometry_msgs/Twist` 订阅，收到 0 帧，据此判定"`nav_cmd_vel_adapter` 把命令拦了"。
> 该话题实际是 **`TwistStamped`** —— **是我的监听器坏了，不是适配器。**
> 教训：**判定"某一段链路不通"之前，先确认自己订阅的类型对不对**，
> 类型不匹配的表现和"没有数据"完全一样，而且不报错。

`/diagnostics` 给出真正的原因：

```
[xr1_chassis] {|xr1_chassis|ChassisStatus|}
      motor controller can connected = yes      ← CAN 通
      motors enabled                 = no       ← 🔴 轮电机没使能
      chassis status                 = unlocked
      chassis wheel                  = ok       ← 轮子本身没故障
[xr1_chassis] {|DIO_Interface|dio_interface|}
      Emergency Key State = RELEASED     Emergency Active = No      ← 不是急停
      Push Mode State     = PRESSED      Unlock Active    = Yes     ← 🔴 推行模式按下
      Emergency Key Pin   = 129          Push Mode Pin    = 27
```

**推行模式 = 「给人手推机器人用」的模式，它主动断掉轮电机的力。**
所以这不是故障，是机器人正确地拒绝在人手推模式下自己开动。
`Push Mode Pin = 27` 是 **DIO 输入**，即一个物理开关 —— **软件改不了。**

`xr1_chassis` 暴露的服务只有三个：`/start_motors`、`/stop_motors`、`/clear_alarm`
（都是 `std_srvs/srv/Trigger`）。**我没有调用 `/start_motors`** ——
在推行模式下强行给轮子上电，是在人可能正扶着机器人时让它带电。
正确顺序是**先松开推行开关，再使能电机**。

> **顺带的结论**：机器人**此刻已经处于专为手动挪位设计的模式**。
> 所以「人直接把它往前推 ~23 cm」现在是**零成本、零风险**的路径 ——
> 不用松开关、不用使能电机。推完了在地上贴胶带标站位。
